Visão geral

O backlog interno do próprio SSX Desk, acessível por API.

Ticket interno é o registro de trabalho de dev/infra/QA/produto do time que opera o SSX Desk — diferente de chamado, que é o atendimento ao cliente final. Esta API permite que outro sistema (um board externo, uma ferramenta de monitoramento, um pipeline de CI/CD) abra, consulte, atualize e converse por notas com esse backlog, sem precisar logar no portal.

⚠

Este recurso é mais sensível que os demais da API de integração. Chamados, conversas, empresas e funcionários são dado da EMPRESA-CLIENTE; ticket interno é a operação interna do próprio SSX Desk — conceda o escopo só a integrações que realmente precisam enxergar esse backlog, nunca como padrão de toda chave nova.

iO que cada ticket interno carrega

CampoTipoDescrição
title / descriptionstringTítulo e descrição do problema/tarefa.
queueIduuidFila do ticket (Configurações → Filas de Ticket Interno) — obrigatória em toda criação.
status / subStatusstringRótulos cadastrados em Configurações (escopo "Tickets Internos"). Ex.: Novo, Em Andamento, Resolvido.
priority1 a 4Estrelas de prioridade — 1 Baixa, 2 Média, 3 Alta, 4 Urgente. Decide o prazo (slaLimit).
assigneeId / creatorIduuidResponsável e quem abriu o ticket.
slaLimitISO 8601Calculado a partir da prioridade — nunca enviado por quem chama a API.
tagsstring[]Marcadores livres.
qaRejected / environmentRejected / lateDelivery / resolvedAt—Só leitura — fluxo e permissão própria dentro do portal (ver capítulo 03).

iiPré-requisito

Uma chave de API com o escopo internal-tickets:read e/ou internal-tickets:write, gerada em Configurações → Integrações dentro do portal (ver capítulo 02). O endereço base é o mesmo da API de integração completa:

# exemplo — troque pelo domínio real do seu SSX Desk https://suporte.suaempresa.com.br/api/integrations/v1/internal-tickets

Autenticação & escopos

Uma chave por integração, com só os dois escopos deste recurso.

1Gerar a chave

  1. No portal: Configurações → Integrações (exige a permissão "Integrações" ou ser Administrador).
  2. Clique em Nova Chave, dê um nome que identifique a integração (ex.: "Board de Engenharia") e marque só os escopos abaixo.
  3. A chave completa (formato ssx_...) aparece uma única vez, na hora da criação — copie e guarde num cofre de segredos. Não há recuperação depois: perdida, a única saída é gerar outra e revogar a antiga.

2Enviar a chave nas requisições

Authorization: Bearer ssx_a1b2c3d4e5f6... # — ou — x-api-key: ssx_a1b2c3d4e5f6...

3Escopos deste recurso

EscopoLibera
internal-tickets:readListar e consultar tickets internos e suas notas.
internal-tickets:writeAbrir e atualizar tickets internos, e adicionar notas — já inclui leitura.

4Testar antes de integrar de verdade

GET/api/integrations/v1/pingsem escopo
Resposta 200
{ "data": { "ok": true, "keyName": "Board de Engenharia", "scopes": ["internal-tickets:read", "internal-tickets:write"] } }

Listar e consultar

Sem filtro ou por qualquer combinação de parâmetros — todos somam (E lógico).

GET/api/integrations/v1/internal-ticketsinternal-tickets:read

Com id, devolve o ticket + todas as notas (sem filtro de visibilidade — ticket interno não tem "nota visível ao cliente"). Sem id, retorna uma página filtrável.

ParâmetroOndeDescrição
idqueryRetorna esse ticket + notas (ignora os demais filtros).
queueId / status / subStatusqueryFila e status do ticket.
priorityquery1 a 4.
assigneeId / creatorIdqueryResponsável / quem abriu.
tagsquerySeparadas por vírgula — qualquer uma basta.
search / contentSearchqueryTrecho do título / da descrição.
createdFrom / createdTo / updatedSincequeryISO 8601 — filtro de data e sincronização incremental.
limit / offsetqueryPaginação. Padrão 100, máximo 500.
Exemplo — detalhe com notas
GET /api/integrations/v1/internal-tickets?id=a93f1c... # Resposta 200 { "data": { "id": "a93f1c...", "ticketNumber": 1532, "title": "Erro ao gerar relatório de SLA", "status": "Em Andamento", "priority": 3, "queueId": "f0a1...", "assigneeId": "c3d4...", "slaLimit": "2026-11-21T18:00:00.000Z", "messages": [{ "id": 7421, "authorId": "c3d4...", "content": "Reproduzido em homologação...", "createdAt": "..." }] } }
✓

Sincronização incremental: GET ?updatedSince=2026-11-01T00:00:00Z&queueId=f0a1.... Guarde o horário em que a rodada terminou (não em que começou) e use esse valor na próxima — assim nenhuma mudança fica de fora.

Abrir ticket interno

Fila obrigatória, prazo calculado, criação à prova de reenvio.

POST/api/integrations/v1/internal-ticketsinternal-tickets:write
CampoOndeDescrição
titlebodyobrigatório
descriptionbodyobrigatório
queueIdbodyobrigatório — fila precisa existir e estar ATIVA
prioritybody1 (padrão) a 4.
assigneeId / creatorIdbodyOpcionais, se já conhecidos.
tagsbodyArray de marcadores livres.
expectedPublishDatebodyData prevista de entrega (estimativa própria — não é o SLA).
creationRequestIdbodyUUID por tentativa de criação (ver abaixo).
Exemplo de requisição
POST /api/integrations/v1/internal-tickets { "title": "Erro ao gerar relatório de SLA", "description": "Relatório trava em \"Carregando\" para período acima de 90 dias.", "queueId": "f0a1...", "priority": 3, "tags": ["bug"], "creationRequestId": "6e2c0d2e-..." } # Resposta 201 { "data": { "id": "a93f1c...", "ticketNumber": 1533, "status": "Novo", "slaLimit": "2026-11-22T12:00:00.000Z", "createdAt": "2026-11-19T12:00:00.000Z" } }
i

Prazo (slaLimit) sempre calculado a partir da prioridade — nunca enviado por quem chama a API. creationRequestId é um UUID seu, um por tentativa: reenviar a mesma requisição (retry de rede) nunca cria um segundo ticket, só devolve o que a primeira já criou.

Atualizar ticket interno

Atualização parcial — envie só os campos que vão mudar.

PATCH/api/integrations/v1/internal-tickets?id=internal-tickets:write
CampoOndeDescrição
idqueryobrigatório
title / descriptionbodyNovo título/descrição.
statusbodyPrecisa ser rótulo cadastrado em Configurações.
subStatusbodyPrecisa ser filho do status informado (ou do atual).
prioritybody1 a 4 — recalcula o prazo automaticamente.
tagsbodySubstitui os marcadores.
assigneeIdbodyNovo responsável.
queueIdbodyReatribui a fila (nunca remove).
expectedPublishDatebodyNova data prevista (null limpa).
Exemplo — marcar como resolvido
PATCH /api/integrations/v1/internal-tickets?id=a93f1c... Authorization: Bearer ssx_... Content-Type: application/json { "status": "Resolvido" } # Resposta 200 { "data": { "id": "a93f1c...", "status": "Resolvido", "updatedAt": "2026-11-19T16:00:00.000Z" } }
⚠

A fila nunca pode ser removida, só reatribuída para outra fila ativa — um ticket que já tem fila não volta a "sem fila" por esta API, mesma regra do portal. Status inexistente em Configurações devolve 400 VALIDATION_ERROR, sem gravar nada.

Notas — ver e adicionar

Toda nota de ticket interno é interna por definição — não há filtro de visibilidade.

GET/api/integrations/v1/internal-tickets/messagesinternal-tickets:read
ParâmetroOndeDescrição
internalTicketIdqueryobrigatório
Exemplo
GET /api/integrations/v1/internal-tickets/messages?internalTicketId=a93f1c... # Resposta 200 { "data": [ { "id": 7420, "authorId": "b7e1...", "content": "Abri este ticket a partir do chamado #4821." }, { "id": 7421, "authorId": "c3d4...", "content": "Reproduzido em homologação..." } ], "meta": { "total": 2 } }
POST/api/integrations/v1/internal-tickets/messagesinternal-tickets:write

O criador e o responsável do ticket recebem o mesmo e-mail de aviso que já recebem quando a nota vem do portal.

CampoOndeDescrição
internalTicketIdbodyobrigatório
contentbodyobrigatório — aceita HTML simples
authorIdbodyAutor da nota, se conhecido.
Exemplo
POST /api/integrations/v1/internal-tickets/messages { "internalTicketId": "a93f1c...", "content": "Correção aplicada, aguardando deploy.", "authorId": "c3d4..." } # Resposta 201 { "data": { "id": 7422, "content": "Correção aplicada, aguardando deploy.", "createdAt": "2026-11-19T17:00:00.000Z" } }
!

Esta versão não aceita anexo binário — imagem colada em base64 dentro do content é extraída e salva automaticamente, mas pra referenciar um arquivo já hospedado em outro lugar, inclua a URL no próprio texto da nota.

Exemplo de consumo real

Um sistema de monitoramento abrindo e acompanhando um ticket, do alerta à resolução.

1
Alerta dispara → abre o ticket
O sistema de monitoramento detecta a falha e abre o ticket já na fila certa, com um creationRequestId próprio — se o alerta repetir por timeout, nunca duplica.
POST /api/integrations/v1/internal-tickets { "title": "CPU acima de 95% — servidor de embeddings", "description": "Alerta do Zabbix às 03:12. Processo node consumindo 97% de CPU por 12min seguidos.", "queueId": "f0a1...", "priority": 4, "tags": ["infra", "alerta-automatico"], "creationRequestId": "c2b6e4b0-2026-11-20-cpu-alert" } → 201, id "a93f1c...", ticketNumber 1601
2
Analista assume → sistema registra a nota
Quando o próprio portal atribui o ticket (ou outro sistema informa quem assumiu), o monitoramento grava uma nota de acompanhamento.
POST /api/integrations/v1/internal-tickets/messages { "internalTicketId": "a93f1c...", "content": "Pico de CPU associado ao job de reindexação de embeddings — reiniciado o scheduler." } → 201, id 9011
3
Dashboard externo sincroniza o progresso
Em paralelo, um painel interno de operações lista as notas pra exibir a linha do tempo do incidente, sem depender de abrir o portal.
GET /api/integrations/v1/internal-tickets/messages?internalTicketId=a93f1c... → 200, 2 notas (abertura automática + ação do analista)
4
Métrica normaliza → fecha o ciclo
O monitoramento confirma que a CPU normalizou e atualiza o status — o criador e o responsável recebem o e-mail de atualização automaticamente.
PATCH /api/integrations/v1/internal-tickets?id=a93f1c... { "status": "Resolvido" } → 200, status "Resolvido"
5
Rodada seguinte — só o que mudou
A próxima sincronização do painel usa updatedSince com o horário em que a última rodada terminou, em vez de reler o backlog inteiro.
GET /api/integrations/v1/internal-tickets?queueId=f0a1...&updatedSince=2026-11-20T03:30:00Z

Erros & checklist

Confira antes de ligar a integração em produção.

StatusCódigoQuando acontece
401UNAUTHORIZEDChave ausente, inválida ou revogada.
403FORBIDDEN_SCOPEChave sem internal-tickets:read/write.
400VALIDATION_ERRORCampo obrigatório ausente, queueId inexistente/desativado, priority fora de 1–4, ou status/subStatus não cadastrado.
404NOT_FOUNDO id/internalTicketId informado não existe.
429RATE_LIMITEDMais de 120 requisições/minuto para essa chave.
500INTERNAL_ERRORFalha inesperada do servidor.
  • ✓ Chave criada com só os escopos necessários (internal-tickets:read e/ou write) — nunca "por garantia".
  • ✓ Todo POST de criação envia creationRequestId próprio — retry de rede nunca duplica o ticket.
  • ✓ Sincronização recorrente usa updatedSince, nunca relê o backlog inteiro a cada rodada.
  • ✓ A plataforma parceira trata 429 com espera e nova tentativa, em vez de descartar a chamada.
  • ✓ A chave fica guardada num cofre de segredos — nunca em código versionado.
  • ✓ Chamada feita sempre do backend da plataforma parceira, nunca do navegador do usuário final.
