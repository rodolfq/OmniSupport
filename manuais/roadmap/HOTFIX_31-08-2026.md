## 2. Descobertas técnicas por item (investigação read-only)

### Bloco 1 — baixo risco, só UI/código local

1. **Prioridade padrão "Baixa"** — `'Média'` hardcoded em `app/api/chat-sessions/route.ts:321` (fluxo chat→chamado). No formulário manual (`new-ticket-modal.tsx:246-250`), o default depende de `availablePriorities[0]`, cuja ordem não é garantida (`config_priorities` não tem `sort_order`, `GET /api/config` não usa `ORDER BY`) — hoje "funciona" por acidente (ordem de inserção do seed: Baixa, Média, Alta, Urgente).
2. **Remover "Categoria" dos chamados** — aparece só em `new-ticket-modal.tsx:511-527` e `ticket-detail-modal.tsx:1259-1270`/`:1535-1537`, sempre separada de Tipo de Solicitação e Produto. Nunca obrigatória (`app/api/tickets/route.ts:409` já usa `categoryId || null`), sem uso em filtros/colunas da listagem nem na API de integração externa além de validação opcional.
3. **Indicador "Baixa" branco no dark mode** — seed de `config_priorities.color` em `schema_postgres.sql:1187-1190` usa classes sem variante `dark:` (ex.: `bg-slate-100 text-slate-600`). O padrão correto já existe em `components/tag-manager.tsx:12` (`bg-slate-100 dark:bg-[var(--surface-pill)]`).
4. **Chat Interno — data da mensagem** — `app/(portal)/chat-internal/page.tsx:1783` usa `<ClientTime date={msg.timestamp} />` sem `showDate`; o mesmo arquivo já faz certo na linha 1445 (`showDate showTime`, painel de fixadas).
5. **Chamados — refresh automático** — `app/(portal)/tickets/tickets-view.tsx:406-412` não tem `refreshTrigger` nas deps do efeito de carga (diferente de `my-tickets/page.tsx:131`, que já funciona).
6. **Push mobile — ícone** — `public/sw.js:24-34` usa o mesmo PNG (`/branding/iconnobg.png`, com fundo opaco) pra `icon` E `badge`. O `badge` precisa de um asset novo, pequeno, só com alfa/silhueta (sem fundo sólido), porque o Android usa só o canal alfa pra desenhar o ícone da barra de status.

### Bloco 2 — comportamento/lógica

7. **Chat Cliente — mensagem editada** — badge "(editado)" exposto ao cliente sem gate em `components/chat-widget.tsx:2899-2905` (compare com o gate já existente na linha 2681, pra "Ver conteúdo apagado"). Endpoint `app/api/chats/route.ts:615-635` (`chat-message-history`) devolve o texto original sem checar se quem pede pertence à conversa — achado de segurança adicional.
8. **Chat Interno — som não funciona** — causa raiz confirmada: `app/api/notifications/check/route.ts` nunca consulta `internal_chat_messages`/`internal_chats`, então o evento de origem simplesmente não existe (não é bug de autoplay). `NotificationSettings` (`app/app-context.tsx:28-43`) também não tem uma chave dedicada pra isso.
9. **Chat Interno — última mensagem** — a action `internal-chats` (`app/api/chats/route.ts:515-558`) retorna `messages: []` hardcoded (linha 551); a UI já sabe exibir (`chat-internal/page.tsx:1170-1231`), só falta a query (mesmo padrão de `sessions-summary`, linhas 131-176).
10. **Chat Interno — adicionar membro com busca/múltiplos** — painel atual (`chat-internal/page.tsx:2377-2403` + `handleAddMember:714-737`) é clique único que fecha o painel a cada pessoa, sem campo de busca.
11. **Chat — notificação só ao responsável** — achado mais sério do levantamento: `lib/services/notification-recipients.ts:94-104` (`getChatRecipientIds`) nem recebe `assigneeId` — notifica **todo o time** (Administrador+Equipe+Time Interno) sempre que quem manda é o cliente, ignorando fila e responsável. Call sites: `lib/services/whatsapp-service.ts:971`, `lib/services/meta-whatsapp-service.ts:279`, `app/api/chats/route.ts:1017`.
12. **Chamados — solicitante principal padrão** — não existe "contato sem login" separado no schema, tudo é `profiles`. `new-ticket-modal.tsx` já auto-preenche quando quem cria é o próprio Cliente/Funcionário (linhas 209-213), mas nada é pré-selecionado quando quem cria é Admin/Equipe.
13. **Status simplificado ao cliente + detalhe restrito (itens reconciliados)** — `my-tickets/page.tsx:38-53` hoje expõe 6 chips crus; `ticket-detail-modal.tsx:1522` mostra `{ticket.status}` cru pro cliente. Grid de resumo do cliente (`ticket-detail-modal.tsx:1517-1544`) hoje mostra Status, Prioridade, Número, Categoria e Data de Abertura.
14. **Giro — não contabilizar fim de semana** — não há filtro de dia da semana em `lib/services/giro-service.ts`. `getGiroDay` (linha ~313)/`generateDay` (linha ~349) geram normalmente pra sábado/domingo, e isso "contamina" a ordem de segunda-feira via `getPreviousOrder` (linha ~103), que pega a última data com giro existente.

### Bloco 3 — maior risco/escopo

Há um `TicketService.calculateSLA` morto (`lib/services/ticket-service.ts:76-90`, horas hardcoded, não chamado em lugar nenhum) — ignorar.
17. **Excluir empresa** — já existe soft-delete oficial (`is_active`, `app/api/companies/route.ts:295-311`, exposto na tela) e uma rota `DELETE` física (`:426-464`) **órfã, sem botão**, que só checa `profiles.company_id` antes de apagar — não checa `tickets` (`schema_postgres.sql:389`, `ON DELETE CASCADE`) nem `customer_evaluations` (`:884`, `CASCADE`), que seriam apagados em cascata silenciosamente.

Não existe SSE pra `ticket_messages` (só `chat_sessions`/chat interno têm, via `lib/chat-events.ts`). `handleSendMessage` (`ticket-detail-modal.tsx:574-602`) não trata erro do `loadMessages()` pós-envio.

1. Na máquina que tem Docker, abra um terminal na pasta do projeto (mesmo repositório).
2. Suba um Postgres descartável, isolado da produção:
   ```
   docker run --name ssx-pg-dev -e POSTGRES_PASSWORD=devpass -p 5433:5432 -d postgres:16
   ```
3. Carregue o schema nesse banco novo (nunca no de produção):
   ```
   docker exec -i ssx-pg-dev psql -U postgres -d postgres < schema_postgres.sql
   ```
4. Crie um arquivo `.env.local` na raiz do projeto (não versionado, tem prioridade sobre `.env` no Next.js) com:
   ```
   DATABASE_URL=postgres://postgres:devpass@localhost:5433/postgres
   ```
   Isso mantém o `.env` real (produção) intocado.
5. `npm install` (se for uma cópia nova) e `npm run dev`.
